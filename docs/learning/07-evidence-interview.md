# Part 07 验证证据与面试中的本人贡献

## 学习目标

把“存在代码”“运行接线”“集成验证”“真实模型表现”“本人理解”分开。形成可以被追问的项目介绍，而不是背技术栈。

## 机制解释

函数存在只证明有实现文本，不证明实际入口调用它。测试直接调用归档helper也不能证明SDK摘要前已归档。可靠检查应从真实入口触发，查询独立事实，例如ERP订单数量、Mongo终态、技能文件读回和摘要模型生成前的归档记录。

unit允许fake；integration使用真实业务依赖，但模型可以是声明的测试替身；live才验证真实模型与外部能力。稳定脚本模型适合触发审批和超时分支，不证明真实模型总能选对工具。成功率需要记录全部试验，不能覆盖失败或反复重跑直到拿到好成绩。

receipt记录一次gate的required checks和证据，state.done记录任务完成，review记录用户审阅。三个状态互不替代。plan_guard检查结构，不评判业务正确性。此前T23/T24 live成绩是历史证据，后续改动后的确定性回归不能冒充重新完成了全套live。

当前异步服务应诚实介绍：有独立Agent Protocol进程与任务API，但 [analyst_graph.py](../../infra/agent-protocol/analyst_graph.py) 目前没有模型客户端，不能称为已完成自主LLM异步学习器。完整RSI的冻结评测、候选晋升和回滚也尚未完成。全仓静态检查与前端测试仍有遗留问题，局部修复gate通过不等于全项目质量通过。

## 代码阅读

[verification.md](../plan/verification.md) 先读三种profile与真实模型门槛；[gate.py](../../scripts/gate.py) 只追检查执行、结果解析和receipt生成；[test_t34.py](../../tests/acceptance/test_t34.py) 或 [test_t35.py](../../tests/acceptance/test_t35.py) 选一个，按“触发 → 观察 → 断言”阅读。

进度看 [HANDOFF](../plan/HANDOFF.md) 顶部，遗留问题结合 [修复前评审](../runtime/harness-review-2026-10-01.md) 理解，不把修复前发现自动当成当前未修问题。暂时不读全部gate历史或全部真实试验日志。

## 具体案例

T34不是看到try/except就声称可靠，而是让graph_provider抛错，检查HTTP存在error与一次failed done、Mongo不再running、registry释放且重放不重启。T35让摘要模型生成前查询Mongo，检查完整原文与todos已经存在；这是运行接线的证据。

以上是仓库修正素材，不自动等于你的独立贡献。学习时亲自复述因果、阅读断言；若你亲手改过，再记录改了哪里、失败复现和验证结果。

## 本人贡献记录

把内容写成四列：“AI辅助产生的代码”“我做过的设计/审阅”“我能独立解释的实现”“我亲手修改并验证的行为”。不确定的地方保留空白。不会函数名可以查资料；机制不懂不要靠术语补。

两分钟介绍结构：业务需求与一个具体案例 → 总体实现链路 → 本人真实参与 → 一个困难及如何核验 → 当前边界。尚未实现的能力用“计划”描述，不用“已实现”。

## 自检

1. 一个绿色单元测试能证明真实ERP下单成功吗？
2. 只调用helper的测试为什么可能漏掉运行接线？
3. done、review、用户理解分别代表什么？
4. 哪一项改进是你能定位、解释、独立验证的？

核对要点：替身与真实业务证据不同；实际入口可能不调用helper；任务证据、人工审阅、个人掌握不同；最后一问必须用自己的事实回答。

## 面试表达

“这是AI辅助搭建的采购助手Demo。我主要参与了……，并对……做过独立验证。比如……故障，我们通过……机制处理，用……事实检查结果。目前……仍是后续工作。”填入真实经历，不能直接照搬成已做贡献。
