# T43 目标修订与已写订单差量重规划

## 目标
约束/来源变化后保留已写订单、按累计预算/数量/交期检查追加量，旧审批失效；新方案逐单重新批准，避免重复采购。模型仍自己选择追加候选，无固定求解器替代。

## 前置与必读
T37/T39/T40/T41/T42；execution/HANDOFF、check→next→packet；planning/chat/ERP契约、Actor入口与场景提案。

## 文件边界
planning模型/checker/orders/revisions、独立judge、规划API/工具和必要chat stale中断恢复；tests/acceptance/test_t43.py及契约/交接。Vue编辑另包；T38代码/服务不运行，不调用付费模型。

## 实现步骤
版本化追加commitments字段，只由控制面从真实已写订单生成；冻结成交价和写入时计划交期/来源，当前报价不重定价历史单。累计checker及独立穷举judge支持追加候选，已写量扣需求、已花费用扣总预算。新revision保存原问题/来源、依赖affected_parts元数据；CAS锁住revision/proposal/orders/执行状态，不确定写入不能修订。PATCH目标接受预期revision、预算/局部Demand更新及指定物料真实ERP刷新；不能直接提交Offer/commitment或身份。核验每个已写ERP订单内容与批准载荷，异常/丢单/外部改写拒绝修订。新候选只形成差量草案，旧审批/旧grant失效。正式chat可从已过期的planning中断继续新用户请求，不以模型resume自批；Episode与bank仍沿用。

## 验收条件
至少15项新增：真实订单累计量/成本、追加不重买、真实ERP读回/外部改写拒绝、预算低于已花/需求低于已订/缩短交期冲突、来源改价不重定历史单、跨供应商/部分规则累计校验、独立judge接受合法并列追加解、小实例穷举对照、局部来源刷新与历史保留、并发CAS、旧审批失效、新审批实际订单、正式API stale中断重规划/同Episode和bank、unknown执行阻止修订、owner/模型scope拒绝。明确scripted模型仅组件，真实Mongo/Java/MCP；原T37/T39/T40/T41回归至少104，不降低原业务断言。

## 完成证据
完整receipt/JUnit、真实ERP内容/数量/金额、state/HANDOFF，review保持not_reviewed。完整Actor/kernel/学习空间/Curator/迁移/动态异步与refinement仍待独立实测。
