# T39 版本绑定的逐单审批与真实多订单执行

## 目标
按用户明确要求暂停 T38，先完成不依赖 kernel 的多单审批组件。输入是 Actor 提交的合法 Plan，系统只校验和拆单，不代替 Actor 求解。完整真实 Actor 场景另包依赖 T38 和本包；学习及持续目标的能力和验收仍保留。

## 前置与必读
T37、T12、T35；planning、mcp、storage-sandbox、verification、实施现场。execution/HANDOFF，check → next → packet。

## 文件边界
src/agent/planning/orders.py、审批记录/服务的版本检查扩展、MCP签名与执行前校验、必要集合索引、应用接线、tests/acceptance/test_t39.py、相关契约/运行文档。冻结 T38 代码和验收。

## 实现步骤
1. Mongo 持久保存 owner/thread/goal 的当前问题、revision、候选和逐供应商草案；验证 Plan，仅产生草案，无自动求解。
2. 每单独立 pending action、payload hash、operation_id，记录 goal/revision/proposal；恢复同方案复用原审批，不产生额外订单。
3. 用户逐单批准/拒绝；审批服务授权和 MCP 写入前均检查当前版本。新版本或不同候选撤销旧批准的执行能力，即使旧 grant 尚未到期。
4. 目标文档 CAS 执行租约，执行中禁止修订；网络结果不确定时保留租约并仅允许同操作对账重试，不能因超时宣称无写入。执行成功保存实际 order_id；已有订单需后续对账，不能重新全量下单。
5. 用真实 Mongo、独立 MCP 服务与 Java ERP 验证两供应商逐单写入、重放、拒绝和旧版本；不调用模型，不启动 kernel。

## 验收条件
至少12项检查，包括真实两单内容和无额外写入、单独批准、不批准/拒绝不写、owner/thread隔离、非法方案、预算修订撤销旧批准与已签grant、同revision换方案撤销批准、重启恢复稳定operation、执行/修订并发、网络不确定保持锁、重试同操作、部分执行不重新批量采购。原T12和T07回归保持。不能称完整Actor/学习/持久计算通过。
