# 用户代码审阅与学习路线

## 按业务链路阅读

1. T02/T03：从 Controller 到事务，理解金额、外键、唯一键、版本冲突和幂等。亲自用新数量创建一次订单。
2. T04/T11：从 MCP schema 到工具对象，再到 YAML 子 Agent。确认分析专家没有写权限，调用用真实业务数据。
3. T08-T10：区分 SDK 适配、稳定 proxy、用户生命周期、虚拟文件路由。删除一个 Demo 沙箱观察恢复。
4. T12/T13：跟一次缺字段到批准的 trace，查看 checkpoint、pending_action、operation_id、Java 写入以及 SSE。
5. T16/T17：读取实际生成的 SKILL.md 和脚本，检查测试如何执行、版本如何持久化、重启如何恢复。
6. T18-T20：理解偏好更新、上下文压缩、调用预算与异步任务的不同生命周期。

## 每包五个问题

- 这次交付的输入、输出、失败结果是什么？
- 哪个实际系统保存事实，重启后证据还在吗？
- 测试换一个未见过的有效输入仍能通过吗？
- 哪段使用了 fake，live 模式如何保证不会进入它？
- 谁能修改这个状态，重复请求和另一用户会发生什么？

## 高风险必看

金额不能 float；订单批准前无数据库写；审批绑定冻结参数；拒绝之后模型重试不能跳过审批；同操作ID不能产生双单；摘要不删展示历史；沙箱错误不在宿主执行；技能半写不发布；用户标识不从模型输入信任。

看验收代码是否直接检查这些事实，不能只检查 mock.assert_called 或最终回答。对 gate.py 和关键断言的修改应单独审阅，任何“临时跳过”都要追问实际阻塞。

## 当前成稿供确认的补齐细节

用户已确认十项访谈选择。本方案进一步固定 Java 21 + Boot 3.5 + H2 文件库、演示账号、单worker并发边界、具体业务schema和验收门槛，以便低成本模型不再猜。它们是缺失实现的设计，不是讲义原代码事实。整体审阅可调整这些细节；未经用户批准不做课程技术替换。

代码实现阶段的 task done 仅代表自动验收有证据，不代表用户 accepted。用户最后可以要求一次新的现场任务；不要只播放保存的视频证明当前版本可用。
