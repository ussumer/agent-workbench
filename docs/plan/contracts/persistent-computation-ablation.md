# T68 持久计算的配对消融协议

唯一干预变量是 `computation_execute` 调用间派生 JSON 的可用性。A 保留 Mongo 已提交派生数据；B 每次调用完成后淘汰派生数据，下一次需从同样原始资料和历史重建。不是撤销 Python 工具，也不是活 Python kernel 与新进程的比较。

两臂同模型/配置、任务与公开规则、初始来源/订单、工具名称/schema/权限、调用护栏和初始对话。Python 每步都是独立进程。双方保留各自全部对话与工具观察，不能为 B 清空历史或输出；原始来源 `task` 永远可用，不属于计算缓存；保护不可修改的来源副本，避免 B 被迫重新获取资料而混入第二变量。

关闭 Curator、反思反馈、few-shot、学习技能、Selector 和生产技能指针。评分只在运行器侧，模型不读私有答案/控制面/裁判。两臂运行后历史自然分叉，不承诺最终 messages 相同。

在两臂每次计算后同样回收该实验 owner 的容器，下一步用同版本干净 OpenSandbox；A 的数据从 Mongo 加载，B 无派生缓存。这样排除 `/workspace`、`/tmp`、旧 staged JSON 和 Python 全局变量绕过 B 淘汰策略。相同容器重建开销单列，不称生产部署性能。执行记录及 stdout/stderr 继续保留且可分页读取，符合保留对话/观察的要求；不能声称 B 从来没见过旧结果。

任务为冻结 v3 的全部20道开发test（4组×5题），无训练/validation选择；1次重复、A/B各一条轨迹，共20组配对、40条轨迹、120次业务回合（用户明确因时间调整，保留最初三轮计划与attempt）。每条轨迹同一线程：初次规划、来源/订单不变的复核、预算降低10%且revision+1后的重规划。两臂的修订不依赖上一轮模型答案，已有 commitments 不变；使用原私有独立评分器按当前输入重新求解。两臂原始资料及统一公开企业规则无答案注入。该工作负载是合成多轮开发诊断，不是新官方v4或封存测试，不与T65训练收益混用。

按任务/repeat配对并轮换AB/BA顺序。每回合30次模型、36次工具、120图步；没有selector，模型计数只含Actor。失败计入分母，不反复重跑挑最好一次；完全成功定义为三回合全部业务通过，另报末回合通过数及平均分。主要指标：配对完全成功率/末回合得分差，胜/平/负；次指标：模型/工具/计算调用、输入输出token、代码字节、耗时、重建/读取保存次数。以20个任务为配对单位，不能把120回合作独立样本宣称显著性；单次重复不证明稳定优势。

证据必须证明：初态/原始来源/commitments一致；B每次调用后只剩原始task；A确实存在跨调用读取先前写入的派生名（否则报告没有观察到复用）；两臂容器都更换；没有学习/selector调用；工具schema一致；完整配对矩阵与失败、费用、模型身份。不预设A胜出，负结果同样完成实验。

本协议仅影响实验包装器，不修改生产ComputationService事务语义、Java ERP、Mongo线程/订单、MCP权限或T64/T65证据。真实ERP前后快照一致仅证明未改订单；v3 commitments是合成输入，不能冒充ERP真实成交订单或adapter验收。
