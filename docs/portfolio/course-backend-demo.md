# 副项目：在线微课平台后端演示稿

建议时长 5 分钟。只讲优惠券发放这条链路，其他模块作为系统范围说明，不在现场逐个展开。

## 开场（约 30 秒）

> 这是一个基于 Spring Cloud 的在线学习平台，源码有 17 个 Maven 模块，包含认证、用户、课程、学习、积分、优惠券、交易和支付等域。现场我只展示优惠券，因为它同时涉及缓存、消息队列和数据库一致性，最能说明后端设计。

## 正常链路（约 1 分钟）

展示简单架构图：Gateway → Promotion → Redis Lua → RabbitMQ → MySQL → 用户券包。

讲解词：

> 用户点击领取时，Redis Lua 脚本一次完成库存、用户限领计数和待投递事件的预扣。请求返回“已受理”不代表券已经写入 MySQL，真正的用户券是在消费者事务里落库。

## 为什么要这样拆（约 1 分钟）

打开 `receiveCoupon`、Lua、outbox 记录和消费者事务代码。

> Redis 和 MySQL 之间没有一个天然的跨存储事务，所以我没有把 Redis 扣成功直接当成发券成功。待投递事件保证应用在 Redis 预扣后退出时还有机会继续投递；消费者用 message ID 和数据库唯一约束去重，重复消息只能产生一张用户券。

这里可以问面试官一个反问式问题：如果 broker 已经收到了消息，但应用在确认前退出，下一次会不会重复？答案是会重复投递，但不会重复落库，这正是幂等设计要解决的情况。

## 故障演示（约 2 分钟）

先运行正常领取，再做两个短场景：

1. 停掉或阻断 MQ，领取请求仍记录待投递事件；恢复 MQ 后事件继续处理。
2. 重放同一个 message ID，查看数据库中只有一条用户券，发放数没有重复增加。

如果现场环境不适合真的停 MQ，使用已保存日志和数据库查询重放，但要明确说是回放，不要把脚本输出说成刚刚发生的真实故障。

## 收尾（约 30 秒）

> 这个项目让我处理的是分布式状态和失败边界，而不是只把几个接口串起来。当前文档记录了哪些链路做过端到端演练，哪些还只是打包和配置检查；并发容量和云端故障恢复没有被我用打包成功来代替。

## 不要现场承诺的内容

- 没有实际压测就不要报吞吐量和 P95。
- 没有端到端演练的支付、搜索、媒资和考试模块只介绍代码范围。
- 不要说“Redis 和数据库强一致”；准确说法是预扣事件、消息投递和数据库幂等共同降低跨存储失败风险。
