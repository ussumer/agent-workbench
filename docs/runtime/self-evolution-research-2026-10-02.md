## 补充核查发现

- 最新评测 SSE 只包含四次主代理工具开始事件，没有子代理 ERP 工具事件。模型网关保留请求哈希和 usage，但不保留完整请求响应；报告中的四次工具调用不能解释为主子总调用次数。TRACE 的行动轨迹需要补齐结构化导出。
- 评测 clarification 当前检查是否消费了预设补充回复，没有核对实际缺失字段是否正确。它能验证交互闭环，尚不能充分验证澄清质量。
- `approval/middleware.py` 在写通道未抛异常时调用 `finish(ok=True)`；业务结果若以 `ok:false` 返回，可能与 ERP 结果记录的失败不一致。自进化标签必须结合业务结果，不能单凭审批 executed。该错误分支本轮未运行复现。
- `approval/service.py` 的授权状态分支显式拒绝 pending/rejected，并处理 pending/approved 超时，但没有统一的可授权状态白名单。已 expired/failed 状态是否能通过业务入口到达重新签票据，需要单独验证；当前不宣称可以绕过审批。
- `user_skills_restore.py` 只安装当前 assignment，没有同步移除已撤回技能；没有 assignment 时提前返回。撤回指针后旧执行目录可能仍被发现。其替换流程使用固定 staging 路径和两次 mv，也不能直接证明跨线程读取到完整不可变版本。本轮为静态链路核查，未执行并发复现。
- 大工具结果 offload 会产生 `ok:true` 的引用信封；学习采集应保留压缩前的业务结果和内容哈希，不能把引用信封当业务成功。当前 uploader 返回结构化错误时是否被充分检查也需验证。
- 当前共享技能 namespace 的 Store search 不过滤返回 key，模型文件挂载还有独立 owner 路径保护，不能据此宣称当前模型可读他人技能。新增 Curator 或经验检索调用 search 时，必须明确 owner、experiment 和 split 限制。
- 现有异步库存分析图无模型，不是现成 Curator。其远程运行预占、在途轮询状态竞争需要另行验证；不宜直接复用为自动学习执行器。
- gate 的源码指纹不覆盖技能 Markdown、完整基础设施和依赖配置。评测已有独立源码副本机制，但演化还需保存完整技能和策略 manifest。

上述问题决定演化所需证据与冻结机制的设计，不在本轮擅自修复。

2026-10-03 补齐技能与产件模块的全文核查：

- 预置分析技能与 analyst 配置已指定抓取、脚本和报告流程；`build_report.py` 固定最低价及供应商 ID 排序，`fetch_quotes.py` 依赖 `section#quotes` 和 `data-*` 属性。若只测试现有同构输入，主要衡量流程执行；要证明技能学习，需要真实的新格式、异常或规则组合，且明确现有业务支持范围。
- `OwnerScopedStoreBackend` 的模型文件写、编辑、删除接口限制 owner 路径，却没有把该 owner 的已发布技能版本设为只读。发布服务的版本约束不能直接当作模型不可修改的权威状态保证；候选、快照和评估结论应由受控服务保存。
- 采购脚本验证已有独立金额与非法输入案例，但指导性技能仍明确记录 `behavior_verified=false`。安装验证和封存泛化评测必须保持不同结论。
- 技能安装和产件注册已有内容哈希，但尚未形成跨技能整体快照及 episode/candidate 关联；产件读取也没有统一重新核对内容哈希。这些能力可以复用，但不足以单独构成演化证据链。

| --- | --- | --- |
| [Prime Agent v1](https://arxiv.org/html/2608.23552v1) | 持续状态及其版本、来源、边界更新和恢复 | 在既有 Mongo、归档与技能存储上增加可审计状态版本；完整 RLM 与递归编排是否采用另行决定 |
| [TRACE v2](https://arxiv.org/html/2608.22793v2) | 按技能组织成功和失败轨迹，对照修订行为知识，记录逐轮技能选择 | 新增 Curator、技能使用证据与候选补丁；保留适用条件，去除具体任务答案 |
| [GDPevo v1](https://arxiv.org/html/2608.03764v1) | 学习任务覆盖业务规则子集，测试任务重组规则，独立判分 | 采购规则与策略覆盖矩阵、学习/验证/封存任务、冻结版本后的迁移评测 |

GDPevo 原协议包含从反馈推断隐藏企业惯例。采购适配现有文档则要求政策、审批和权限公开。二者不能直接等同：公开规则下的策略组合泛化可以作为改造实验；若测试隐藏惯例学习，必须另建明确实验条件，且不能隐藏或改变强制审批和权限约束。

完整移植 Prime 的 REPL、递归子代理、持续目标与直接通信，会改变运行架构和可用计算量。若采用，应与技能演化分开做消融，并保持可比较预算。持久化状态本身不等于已验证的能力提升。

## 必需接口与待定实现

1. 完整任务记录：关联一次业务目标及其多个 API run/resume、主子代理调用、工具参数结果、技能读取/采用证据、业务评分和资源消耗。保留 Actor 当时可见信息；诊断特权信息单独标注。
2. 技能库快照：记录技能及策略版本与内容哈希；一次任务跨审批恢复保持相同快照。仅在 Mongo 记录版本、却继续读取原地变更的执行目录，不构成冻结。
3. 学习接口：只接收声明允许的反馈和学习任务轨迹，产出候选而非直接替换生效技能。采购偏好与学习策略保持不同语义和存储入口。
4. 晋升接口：绑定父版本、来源记录、独立评估与决策；条件更新活动版本，并记录回滚。现有发布流水线的安装验证不等于行为改进验证。
5. 评测接口：固定源码、模型配置、业务初态和技能快照。各实验组权限一致；测试前不提供答案或裁判，测试后不把结果写回下一测试任务的快照。

技能选择、技能正文读取、脚本执行和最终任务成功是不同证据。TRACE 式分组至少需要可追溯的技能采用记录，不能用目录里存在某技能代替。

实验组还需要区分两个独立维度：记忆/技能更新方法，以及允许的监督反馈。采购适配的 A/B/C/D 是前者；GDPevo 的 base/fewshot/self/reflect-3 主要区分训练经历和监督信息，不能一一等同。官方本地协议中的 acc@3 是三次分数均值，不能称为至少一次成功的 pass@3；TRACE 的全部重复通过指标也应独立实现。

TRACE 隐藏集结果同时报告准确性提升与 token、延迟、单次费用增加，不能默认技能演化能降低费用。GDPevo 把一次性技能生成成本与测试执行成本分列。采购适配应同时报告这两类成本及总成本，而非只挑有利列；重复运行还应分别报告平均成功、至少一次成功和全部通过，不从平均成功率简单推算一致性。

评测预算网关已累计主子模型请求，但未来 Curator 必须同样纳入预算。该网关先读完上游响应再返回 SSE，整任务耗时可记录，不能据此测真实首 token 延迟。verify 的 passed 表示组件与留存证据检查通过，不表示全部历史任务业务成功。

## 首期接入草案

本节是已确认边界的研究摘要，完整要求以已接受的实施规格为准。业务实现保持现有技术栈，新增演化基础设施不等于允许学习器修改 Harness 代码。

### 数据与执行闭环

1. `Episode` 聚合一个业务目标跨多次 run/resume 的记录，包含主子调用、审批、业务前后状态、当时实际采用的技能版本和资源消耗。模型自评不作为独立成功标签。
2. 独立评分器输出 `Feedback`：任务结果、固定失败类别、公开规则 ID 与证据引用。预期订单、封存输入与裁判实现不给学习器。
3. `Curator` 只处理 train 的已完成 Episode；先按操作或技能分组，对成功与失败轨迹作比较，再提炼适用条件、处理步骤、失败边界与检查点。没有成对轨迹时标记证据不足，不凭空构造失败案例。
4. 输出 `Candidate`：父快照、来源 Episode、修改的策略正文、适用条件、支持与反例证据、变更原因。移除具体订单答案、敏感信息和实例 ID；业务权限与审批规则不能由候选修改。
5. 候选单独冻结，使用 validation 与预先固定的旧能力集合评估。晋升只依据这些结果；sealed_test 不参与候选选择和继续修订。
6. `Promotion` 通过服务在实验活动指针上条件更新，保留父版本与决策证据。日常 Demo 的活动指针独立，需要人工确认；任务跨审批恢复仍使用原冻结快照。
7. 最终一次性冻结所选版本，独立执行 sealed_test，并报告所有尝试。学习成本、候选评估成本、最终测试成本分别报告，另列总成本。

### 三篇工作的分工

- TRACE：作为成功/失败轨迹比较、技能修订和去除实例答案的机制参考。若只使用官方 Skill 发现而不实现论文的逐轮状态条件技能选择与注入，应明确称为 TRACE-inspired，而非完整复现。
- Prime Agent：首期采纳持久策略的版本、来源、任务边界更新与回滚；完整 REPL/RLM 和递归编排不在首期演化范围。Prime-inspired 状态治理不等于完整 Prime Agent 架构。
- GDPevo：参考学习任务覆盖规则子集、测试重组与独立判分。当前公开业务规则下的执行策略泛化，与论文隐藏企业惯例的学习条件分别说明，项目结果不借用论文结果。

### 已确认对照（第四轮）

| 组 | 可跨任务保留的内容 | 要回答的问题 |
| --- | --- | --- |
| A 固定技能 | 初始技能，无学习更新 | 固定 Agent 的真实业务基线 |
| B 原始经验检索 | train 执行记录与允许反馈，不自动修订技能 | 直接复用经历是否有用 |
| C 策略提炼 | 从相同 train 记录提炼和修订的技能文字 | 提炼是否优于仅检索经历 |

各组共享 Actor 模型配置、工具权限、任务与业务初态，冻结后禁止学习。经验/技能输入设置共同 token 上限，记录实际检索内容、使用情况和上下文成本；基线不填充无用文本来假造完全一致输入量。B 与 C 允许的监督信息相同。C 的额外学习计算独立计费，不能声称三组总计算量天然相等。

若 C 有增益，后续再加“仅成功轨迹”与“成功/失败对照”的消融，验证对照修订本身的贡献。首期 A/B/C 不直接映射论文监督条件，也不沿用旧适配器 A/B/C/D 字母的隐含定义；实现前必须版本化更新组定义与兼容策略。
