# 场景升级提案：多约束补货规划与异常重规划

状态：用户已在 2026-10-03 明确要求按本文方向实施；具体推进见 [实施现场](procurement-planning-implementation.md)。不授权新增付费调用。现有课程能力、技术栈、审批与业务数据保持。

## 业务目标

从“用户给定订单参数，助手办理订单”，升级到“用户给目标与约束，助手收集证据、比较可行方案、解释取舍，经审批后创建实际采购订单”。

第一版使用 CNY、piece、已有供货关系、目录交期、库存预警与目标库存。增加任务输入的预算、截止时间、物料优先级与允许分批规则，不先引入税费、收货或付款系统。交期是计划依据，不声称下单后验证实际到货；下单仍不改变库存。

## 具体可演示实例

基于现有 seed-v1 生成新的实验任务：预算 2500 元；P001 必须补足 42 件，计划交期不超过 3 天；P003 必须补足 15 件，交期不超过 7 天；剩余预算尽量补 P004 至目标，但允许其分批，交期不超过 7 天。所有约束公开。

- 原最低价建议选择 S002 的 P001，但目录交期 4 天，不能满足 P001 的期限；应选择 S001 的 25.50 元、3 天。
- P003 的可用供应商是 S001，15 × 68.00 = 1020.00 元。
- 两项必需需求花费 42 × 25.50 + 15 × 68.00 = 2091.00 元。
- 剩余 409.00 元；S002 的 P004 单价 17.50、交期 6 天，可买 23 件，花费 402.50 元。
- 方案总额 2493.50 元，P004 尚缺 7 件。应明确报告缺口，不声称全部补足。

此任务的目标顺序事先固定：满足必需物料数量与交期 → 在预算内最大化可选物料补足数量 → 最小化花费 → 固定并列解规则。不能让 Agent 或评分器各自选择目标。

两家供应商分别形成实际订单，逐单走现有审批。一次业务目标可有多个订单/审批，因此现有 pilot “恰好一个订单”评分契约不能直接复用；保持旧 pilot 不变，新增任务版本与独立评分。

## 为什么这种复杂度有意义

复杂度来自约束交互、证据来源与状态变化，不来自人为添加几十个工具：

1. 价格低与交期短可能冲突；预算可能不足，需事先声明优先级与允许部分满足的边界。
2. 供货关系、活跃状态、库存建议量、页面报价和目录交期要关联，不允许假定缺失字段。
3. 方案有多个合法解，用独立可行性及目标值评分，不能仅与一份固定文本答案比较。
4. 需求或来源变化时，需要保留中间计算并只重算受影响部分；审批冻结参数与规划状态必须有一致关系。
5. 多次不同任务共享可迁移的处理经验，但也有反例，不能把“永远选最低价”“遇到超时就重试”“一律先问用户”固化成策略。

## 三条机制路线

### Prime：持久程序化工作状态

将分析会话的 Python 中间值留在 OpenSandbox 内的持久 kernel，例如标准化报价、供货映射、约束集、候选方案和校验结果。Agent 自己用代码检索、计算、比较，只将必要结果送入下一模型调用。不能用完整固定 planner 脚本代替 Agent 的策略构建。

持久 kernel 是新增运行机制，不是现有 shell 执行已具备的能力。需要依赖签名/版本核实、owner/session 隔离、取消/重启恢复和不可序列化对象重建协议。独立裁判的求解器与答案不能向 Agent 暴露。

后续才研究稳定异步子会话与在线 refinement：例如分派来源核对、可行性分析、反例检查，然后在同一持续目标中交换证据。固定角色、临时委派不称完整 Prime 运行时；没有明确的并行收益前不添加 swarms。

任务中生成一次性计算代码，与把脚本作为可进化 Skill 发布是不同权限。首期可以保持演化产物仅文字；若加入可执行技能或角色配置演化，需另行确认范围。

### TRACE：操作级策略与逐回合编排

学习对象是“如何做可靠决策”的程序知识，例如来源冲突核对、先判断可行性再比价、约束不足时澄清、方案变化时重算及重新审批。不要直接学习某次订单选 S001、买 23 件。

采用论文初始化的任务→类型→操作抽象与聚焦拆分，以及按实际技能选择分组的成功/失败比较、缺失能力发现和去除实例答案。每个 Actor 动作回合根据当前状态重新编排有序技能正文，不用一次静态检索代替。

### GDPevo：先建立可学习关系

将操作知识原子与作用域先写入矩阵。训练分别出现“价格/交期冲突”“预算不足但允许次要物料分批”“来源缺字段”，测试组合这些条件及其交互。增加反事实分支：明确数量时不多余澄清、足够预算时不错误截断、不同期限时不无条件排除供应商。

公开规则下仍可能有策略学习，但不能称隐藏企业惯例学习。若要后一种，另建企业内部条件规则与信息暴露协议：训练存在足以推断的反馈/证据，测试重组，公开审批与权限政策不隐藏。没有可学习结构时改任务设计，不通过改评分制造收益。

## 分阶段实施

| 阶段 | 范围 | 验证 |
| --- | --- | --- |
| S1 约束规划 | 用现有 ERP 字段和明确任务约束，产出方案/缺口/来源；最终审批创建多单 | 独立小实例可行性与最优目标、合法替代解、多订单/审批绑定 |
| S2 证据与状态 | 多种报价材料、来源冲突和缺失；适量扩展独立 seed，持久程序化工作状态 | 中间值跨回合复用、选择性读取、压缩/重启恢复、解析与来源正确性 |
| S3 经验学习 | TRACE 式 Skill Bank、冻结对照、作用域反例 | 固定/原始经验/提炼技能对照，另做简单总结与逐回合编排消融 |
| S4 持续目标 | 需求/报价在批准前发生变化、异步证据核对、受限在线 refinement | 重规划、旧批准失效、稳定会话/消息、时间流评测与资源核算 |

顺序是先证明环境可解且有学习空间，再增加学习算法。S1 可用少量物料/供应商做穷举独立裁判；扩大实例后选择适当求解工具并核实官方文档，不先为规模新增一套复杂优化技术栈。

训练规模、在线更新时间和付费额度单独锁定。先验收一个有约束冲突的完整任务，避免同时扩大业务、运行时、任务量和演化权限。

## 现有代码需要的实质变化

- 增加规划业务目标/约束/方案的契约，保留旧订单与课程分析模式。
- 现有 `build_report.py` 固定最低价流程不能作为新场景完整规划器。可复用读取、金额计算与报告代码；新 planner-mode 由模型组织计算、系统检查约束。
- 现有 `fetch_quotes.py` 依赖 section#quotes 与 data-*，多源材料必须有新的提取与核验路径，不给新材料偷偷补同构隐藏标签。
- Analyst 的现有强制流程要区分课程模式与规划实验模式；基础权限与审批不改变。
- Episode、Snapshot 和评分器支持一个目标的多订单、多次批准及持续计算状态，不能只在原三个 pilot 外围加一层文字。
- 持久 kernel、稳定异步会话与 refinement 分别登记机制任务，组件/真实行为验收和研究消融分开，不以 schema 通过宣称论文能力已实现。
